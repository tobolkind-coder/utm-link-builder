# Code Style

Версия: 1.0

---

# Общие требования

Весь проект должен быть написан на TypeScript.

Использовать строгий режим компилятора (`strict: true`).

Код должен быть читаемым, предсказуемым и соответствовать современным практикам разработки.

Главный принцип — простота и понятность.

---

# TypeScript

Использовать строгую типизацию.

Запрещается:

- использовать `any`;
- отключать проверки TypeScript;
- использовать `// @ts-ignore`, кроме исключительных случаев с обязательным комментарием;
- использовать небезопасные приведения типов без необходимости.

Предпочитать:

- `interface` для описания структуры данных;
- `type` для объединений (`union`) и сложных типов.

Все функции должны иметь явно определённые типы параметров и возвращаемого значения.

---

# Структура файлов

Один файл должен отвечать за одну задачу.

Не размещать несколько независимых компонентов в одном файле.

Предпочитать небольшие и переиспользуемые модули.

---

# Именование

Использовать понятные имена.

Хорошо:

```ts
createShortLink()
findUserByLogin()
generateCampaign()
```

Плохо:

```ts
doWork()
run()
test()
```

Не использовать сокращения, если они ухудшают читаемость.

---

# React

Использовать только функциональные компоненты.

Не использовать классовые компоненты.

Компонент должен выполнять одну логическую задачу.

Если компонент становится слишком большим, разделить его на несколько компонентов.

---

# Hooks

Использовать встроенные React Hooks.

Повторяющуюся логику выносить в собственные Hooks.

Не вызывать Hooks условно.

Соблюдать Rules of Hooks.

---

# Работа с API

Не выполнять HTTP-запросы непосредственно в JSX.

Всю работу с API вынести в отдельный слой.

Например:

```text
src/api/
```

или

```text
src/services/api/
```

---

# Бизнес-логика

Запрещается размещать бизнес-логику:

- в React-компонентах;
- в Route Handlers;
- в Prisma Repository.

Бизнес-логика должна находиться в Service-слое.

---

# Работа с базой данных

Все обращения к базе выполняются через Prisma.

Не использовать Raw SQL без необходимости.

Повторяющиеся запросы выносить в Repository.

---

# Комментарии

Комментарии использовать только там, где код действительно нуждается в пояснении.

Не писать очевидные комментарии.

Плохо:

```ts
// Увеличиваем счетчик
count++;
```

Хорошо:

```ts
// Удаляем старые UTM-параметры перед генерацией новой ссылки,
// чтобы избежать конфликтов с уже существующими значениями.
```

---

# Форматирование

Использовать Prettier.

Не изменять форматирование вручную, если это противоречит настройкам проекта.

---

# Импорты

Использовать логичный порядок:

1. Внешние библиотеки.
2. Внутренние модули.
3. Локальные файлы.

Не оставлять неиспользуемые импорты.

---

# Константы

Не использовать "магические числа" и строки.

Выносить их в именованные константы.

Например:

```ts
const MAX_HISTORY_ITEMS = 15;
```

---

# Обработка ошибок

Не оставлять пустые блоки:

```ts
catch {}
```

Каждая ошибка должна быть обработана.

---

# Асинхронный код

Использовать `async/await`.

Не использовать цепочки `.then()`, если можно использовать `async/await`.

Все Promise должны быть обработаны.

---

# Повторное использование кода

Избегать дублирования.

Если одинаковый код встречается более одного раза, рассмотреть возможность вынесения в:

- функцию;
- сервис;
- утилиту;
- компонент.

---

# Безопасность

Никогда не логировать:

- пароли;
- cookie;
- токены;
- секретные ключи;
- содержимое переменных окружения.

Не доверять данным, полученным от клиента.

Все входные данные должны проходить серверную проверку.

---

# TODO и временные решения

Перед завершением проекта запрещено оставлять:

- TODO
- FIXME
- HACK
- заглушки
- mock-данные

Все функции должны быть реализованы полностью.

---

# Производительность

Избегать лишних запросов к базе данных.

Не выполнять повторные вычисления без необходимости.

Использовать индексы базы данных.

Минимизировать количество повторных рендеров React-компонентов.

---

# Читаемость

Код должен быть понятен другому разработчику без дополнительных пояснений.

Предпочитать понятный код сложным и "умным" конструкциям.

---

# Качество

Перед завершением проекта необходимо убедиться, что:

- проект успешно собирается;
- отсутствуют ошибки TypeScript;
- отсутствуют ошибки ESLint;
- отсутствуют предупреждения линтера;
- код соответствует требованиям данного документа.

---

# Итог

Код проекта должен быть чистым, единообразным, безопасным и легко поддерживаемым.

При возникновении выбора между коротким и понятным решением предпочтение отдаётся понятному решению.
