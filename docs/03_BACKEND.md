# Backend

## Общие требования

Backend отвечает за:

- авторизацию пользователей;
- генерацию UTM-ссылок;
- генерацию коротких ссылок;
- редирект;
- работу со справочниками;
- работу с пользователями;
- настройками сервиса.

Вся бизнес-логика должна находиться только на сервере.

Frontend не должен самостоятельно принимать решения.

---

# Архитектура

Использовать разделение:

Routes

↓

Controllers

↓

Services

↓

Repositories (Prisma)

↓

Database

Не размещать бизнес-логику внутри React-компонентов.

# Авторизация

Использовать сессионную авторизацию.

После успешного входа пользователь получает защищенную HTTP Only Cookie.

Cookie должна иметь:

HttpOnly

Secure (в production)

SameSite=Lax

После выхода сессия уничтожается.

## Алгоритм

1. Получить shortCode из URL.

2. Выполнить поиск записи в таблице Links.

3. Если запись не найдена:

вернуть

HTTP 404 Not Found

4. Если запись найдена:

вернуть

HTTP 302 Found

Location: utmUrl

Использовать только HTTP Redirect.

Использование JavaScript Redirect запрещено.

# Пользователи

Все маршруты доступны только Administrator.

---

## Получить список пользователей

GET

/api/users

Возвращает пользователей, у которых:

isDeleted = FALSE

Сортировка:

createdAt DESC

---

## Создать пользователя

POST

/api/users

Входные данные

```json
{
  "login": "",
  "fullName": "",
  "password": "",
  "role": "USER"
}
```

Проверки

- логин обязателен;
- логин уникален;
- пароль минимум 8 символов;
- пароль содержит минимум одну букву;
- пароль содержит минимум одну цифру.

Перед сохранением пароль обязательно хэшируется с использованием bcrypt.

---

## Изменить пользователя

PUT

/api/users/{id}

Разрешается изменять:

- fullName
- role
- isActive

Логин изменять запрещено.

---

## Смена пароля

PUT

/api/users/{id}/password

При изменении пароля:

- проверить минимальную длину;
- захэшировать новый пароль;
- обновить passwordHash.

---

## Удаление пользователя

DELETE

/api/users/{id}

Использовать Soft Delete.

Выполнить:

isDeleted = TRUE

isActive = FALSE

deletedAt = NOW()

Физическое удаление запрещено.

---

## Ограничения

Запрещается:

- удалить самого себя;
- удалить последнего администратора;
- изменить роль последнего администратора.

# Валидация

Все входящие данные должны проходить серверную проверку.

Клиентская валидация является дополнительной и не заменяет серверную.

Использовать DTO для всех входящих данных.

Не использовать необработанные объекты request.body напрямую.

---

# Обработка ошибок

Все ошибки должны обрабатываться централизованно.

Не выводить Stack Trace пользователю.

В production запрещено возвращать внутренние сообщения об ошибках.

Для пользователя использовать понятные сообщения.

Например:

"Некорректный URL."

"Пользователь не найден."

"Недостаточно прав."

"Короткий домен не настроен."

---

# Импорт справочников

При первом запуске приложения необходимо выполнить проверку таблиц:

- UtmSource
- UtmMedium
- UtmCampaignPart1
- UtmCampaignPart2

Если таблица пуста:

импортировать данные из файлов

/docs/utm_source.txt

/docs/utm_medium.txt

/docs/utm_campaign_1.txt

/docs/utm_campaign_2.txt

Порядок строк определяет sortOrder.

Повторный запуск не должен создавать дубликаты.

---

# Производительность

История ссылок ограничивается 15 записями.

Использовать LIMIT на уровне базы данных.

Не выполнять выборку всех ссылок пользователя.

Выбирать только необходимые поля.

Использовать индексы.

Избегать N+1 запросов.

---

# Логирование

В production запрещено использовать console.log.

Ошибки должны логироваться централизованно.

Логирование не должно содержать пароли, cookie, токены и другую конфиденциальную информацию.

---
